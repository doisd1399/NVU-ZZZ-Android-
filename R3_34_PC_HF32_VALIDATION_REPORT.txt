NVU R3.34 PC-HF32 — CONTINUOUS GTO RECOGNITION
Android 1.0.84 / versionCode 84

ROOT CAUSE ADDRESSED
- HF31 compared Image.getTimestamp() with System.nanoTime() to decide frame age. Android does not guarantee that a media Image producer timestamp shares System.nanoTime()'s absolute timebase. On affected OEM/source combinations this can discard every live detector frame before GtoFastVisualDetector runs.
- The capture stability path also advanced lastProjectionAnalyzedFrameAt without running the screen classifier, allowing the white dot to report healthy while the detector was blind.
- Recognition outside WAITING_FREIGHT was too state-scoped; screen observation and state mutation were coupled.

HF32 CHANGES
1. Image timestamps are used only as same-ImageReader producer ordering. No wall-clock subtraction and no System.nanoTime() comparison.
2. Ordered WAITING_FREIGHT queue remains bounded by ImageReader(3); non-waiting states use acquireLatestImage().
3. White capture-health dot now requires GTO foreground + stable capture + a real classifier heartbeat. Stability-only buffer qualification cannot fake health.
4. The lightweight recognizer also runs while the stability gate is qualifying frames; the gate controls state mutation, never whether GTO is observed.
5. Lightweight OCR-free visual recognition runs every 90 ms in every capture-required GTO state.
6. Recognition is informational by default; deterministic state/human-evidence rules remain the only authority for journey mutation.
7. Semantic result OCR fallback reduced from 1800 ms to 650 ms for near-real-time completion recognition without OCR on every frame.
8. Producer-order baselines reset on geometry/session/surface invalidation.
9. Both exact real user screenshots that failed in HF31 are packaged regression fixtures.
10. HF31 fail-safe floating-button lifecycle protections remain intact.
