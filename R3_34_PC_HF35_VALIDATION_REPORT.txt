1. INCIDENTE QUE MOTIVOU HF35
Durante uma viagem ativa no HUB do GTO, a HF34 classificou uma tela sem lista de fretes como retorno da lista. Como, na lógica HF34, o retorno da lista é a fronteira canônica que encerra a viagem anterior, um falso positivo visual tinha poder destrutivo sobre o estado da viagem.

2. CAUSA RAIZ EXATA
A falha não era apenas um limiar de cor isolado. Existia uma contradição de autoridade entre as camadas:

A) GtoFastVisualDetector.hasFreightList()
- Fazia reconhecimento OCR-free em tempo real.
- Os limiares de textura/cartão eram permissivos o bastante para certas combinações de HUB/HUD produzirem candidato visual parecido com lista.
- Em páginas multi-row, uma única linha forte podia contribuir excessivamente para validar a tela.
- O agregado de cardEvidence existia, mas não era exigido por uma segunda política completa antes de permitir a classificação visual.

B) GtoFreightSemanticCertificationPolicy
- Já existia para certificar semanticamente páginas reais, mas não era autoridade obrigatória para o boundary destrutivo de uma viagem ativa.

C) GtoObserverService.handleActiveTripFreightListEvidence()
- Na HF34, dois frames visuais estáveis por ~55 ms podiam promover a página para retorno de lista e desconsiderar a viagem anterior.
- Portanto: candidato visual -> boundary de lifecycle. Esse acoplamento era a regressão crítica.

D) Sensor de toque
- Um candidato visual falso podia manter armada a infraestrutura usada para correlacionar Aceitar, ampliando a superfície de erro durante a falsa página.

3. NOVA REGRA DE AUTORIDADE HF35
A detecção foi dividida em duas autoridades independentes:

CAMADA 1 — VISUAL / TEMPO REAL
- Continua rodando sem OCR pesado, por frame, para não perder responsividade.
- Pode apenas declarar FREIGHT_LIST_VISUAL_CANDIDATE.
- Não pode cancelar viagem, criar nova sessão, completar resultado ou selecionar frete.

CAMADA 2 — SEMÂNTICA / DESTRUTIVA
- Usa o snapshot congelado da mesma página detectada visualmente.
- A página multi-row precisa repetir evidência semântica em pelo menos duas linhas.
- A autorização de boundary exige também ao menos uma linha completa com:
  Aceitar + distância Km + valor monetário, vinculados à geometria de uma linha visual real.
- Só visual + semântico permitem FREIGHT_LIST_REOPENED_CERTIFIED.

INVARIANTE HF35:
Nenhum pixel, tempo decorrido, geometria isolada, HUB/HUD parecido ou toque isolado pode desconsiderar uma viagem ativa. A viagem só é substituída quando a página congelada é certificada semanticamente como lista real do GTO.

4. MUDANÇAS IMPLEMENTADAS

GtoFreightListEvidencePolicy.java
- Multi-row agora exige pelo menos 2 strong row anchors.
- Uma linha isolada não certifica mais uma página multi-row.

GtoFastVisualDetector.java
- Card texture mais estrita:
  dark >= 0.68
  light text >= 0.014
  green info >= 0.0050
  strong orange >= 0.18
- hasFreightList() exige simultaneamente isPlausibleSimpleList() e isPlausibleList().
- Mantidos alinhamento, largura, coluna e cadência vertical da lista real.
- Uma página real de 1 frete continua suportada.

GtoFreightSemanticCertificationPolicy.java
- Multi-row exige pelo menos 2 anchors Aceitar + valor.
- Novo isCertifiedLifecycleBoundaryPage(): exige página semanticamente certificada e ao menos 1 linha completa Aceitar + Km + valor.

GtoSimpleScreenDetectionPolicy.java
- Novo gate isCertifiedFreightListReturn(): retorno destrutivo requer visual estável + certificação semântica.

GtoObserverService.java
- O retorno visual durante viagem agora só arma candidato não destrutivo.
- OCR semântico da página é disparado imediatamente sobre o painel congelado.
- Certificação possui generation guard, freshness e retry/backoff para impedir callback velho ou mistura de páginas.
- Falha semântica gera FREIGHT_LIST_VISUAL_CANDIDATE_REJECTED e mantém a viagem intacta.
- Candidato rejeitado deixa de controlar o sensor de toque.
- promoteReplacementFreightCandidateToWaiting() possui hard gate isReplacementFreightSemanticFresh() antes de qualquer discardSessionSnapshot/clearTripAnalysis/beginTrip.
- Resultado com Receber latched continua protegido: a entrega concluída é persistida antes do próximo ciclo.

5. COMPORTAMENTO CANÔNICO APÓS HF35

VIAGEM ATIVA + HUB/GAMEPLAY
- Detector visual pode observar a tela continuamente.
- Se houver aparência parecida com lista, vira candidato.
- Sem assinatura semântica real, candidato é rejeitado.
- Viagem permanece TRIP_IN_PROGRESS, sem reset e sem nova seleção.

VIAGEM ATIVA + LISTA REAL REABERTA
- Frames visuais reconhecem a estrutura imediatamente.
- OCR do snapshot confirma a assinatura real da página.
- Após certificação, a lista torna-se boundary canônico.
- Viagem anterior é desconsiderada conforme regra funcional solicitada.
- Nova sessão WAITING_FREIGHT é preparada.
- O motorista ainda precisa escolher Aceitar; nenhuma linha é auto-selecionada.

LISTA REAL + TOQUE RÁPIDO
- O visual continua rápido para preservar o frame de pressão.
- O toque pode ser guardado durante a curta janela de certificação.
- Mesmo um toque exato não pode cancelar a viagem antes da certificação semântica da página pré-toque.

6. TESTES NOVOS HF35
- Multi-row visual requer anchors fortes repetidos.
- Multi-row semântico rejeita um único anchor acidental.
- Boundary destrutivo exige linha completa Aceitar+Km+valor.
- Candidato visual durante viagem é não destrutivo.
- Promotion é impossível sem certificação semântica fresca.
- Certificação usa o snapshot congelado da mesma página.
- Página visual falsa é colocada em quarentena e não controla sensor de toque.
- Screen policy exige concordância visual + semântica.
- Cenários sintéticos HUB/list foram executados na policy Java.
Resultado: 10/10 PASS.

10. CRITÉRIO DE APROVAÇÃO FÍSICA
A correção elimina por construção o poder destrutivo de um falso positivo puramente visual. Ainda assim, MediaProjection, ML Kit e frames são executados pelo Android/OEM real. A aprovação de produção requer reproduzir no aparelho que apresentou o HUB false-positive:
1) viagem ativa;
2) passar/repetir HUB e HUDs;
3) nenhuma mudança de tripState sem lista real;
4) abrir lista real;
5) boundary deve ocorrer rapidamente após certificação;
6) escolher Aceitar;
7) frete exato deve ser coletado e bloqueado;
8) viagem deve seguir normalmente.
