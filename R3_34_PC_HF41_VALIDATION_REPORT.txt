PHYSICAL INCIDENT REPRODUCED
- GTO result modal was recognized: “Concluído / Valor a receber / Receber / Dobrar valor (ADS)”.
- NVU announced “Entrega detectada · toque em Receber.”
- Driver tapped Receber once; GTO immediately closed the irreversible result modal and returned to gameplay.
- NVU remained in RESULT_DETECTED and continued saying “Toque em Receber para concluir a viagem”.
- The trip therefore never crossed the local durable completion gate and was not enqueued for automatic sync.

ROOT CAUSES CONFIRMED IN HF40
1) POST-RESULT OCR VIEWPORT CONTRADICTION
   HF40 kept result-state semantic OCR cropped to the central result region. After Receber closed the modal,
   the transition resolver called looksLikeGameplay(), whose strongest HUD anchors (FPS, km/h, Desligado)
   are on the far-left side of the GTO display. The crop made those anchors invisible. A valid Receber action
   could therefore leave RESULT_DETECTED permanently after the one-time result screen disappeared.

2) IRREVERSIBLE INPUT OBSERVER ARMING RACE
   The independent 1px ACTION_OUTSIDE observer was attached only after entering a result/selection state and
   after state/UI work was posted. A fast driver tap on Receber could happen before that tiny observer existed.
   Because the GTO result modal cannot be reopened after Receber, losing this event is unrecoverable unless the
   subsequent visual transition is itself a valid recovery signal.

3) TRANSITION-CONFIRMED RECEIVE WAS NOT DURABLY LATCHED BEFORE COMPLETION
   One gameplay-return path could call confirmNormalResultAutomatically() without first synchronously storing
   resultReceiveLatched=true. The irreversible external action therefore did not have a guaranteed durable local
   commit boundary before completion/sync side effects.

4) RESULT INPUT WAS OVER-BLOCKED BY NVU MENU STATE
   Result touch handling could be suppressed merely because menuView existed, even when the physical touch was
   outside the NVU card. Only a touch provably inside the NVU card may be ignored.

HF41 ARCHITECTURAL CORRECTION
- Passive 1px outside-touch observer stays pre-armed for the entire enabled + GTO-foreground + overlay-allowed
  session. It is independent of ImageReader/capture-stability recovery.
- Freight mutation remains capture-stability-gated; pre-arming the observer does NOT allow unstable freight
  selection.
- When a semantic result is detected, an expanded NVU menu is closed so it cannot cover Receber.
- Before result action/exit, semantic result OCR keeps the fast central crop.
- After TOUCH_PENDING / exact Receive / durable latch / result exit / certified result-dialog disappearance,
  OCR switches to whole-display mode so gameplay HUD anchors can be seen immediately.
- The existing visual result gate is used only AFTER a result was already semantically certified. It cannot wake,
  create, or confirm a result on its own.
- If OEM delivers ACTION_OUTSIDE, that action is the fastest evidence path.
- If OEM drops/redacts the event entirely, repeated disappearance of the already-certified result modal plus
  repeated full-frame gameplay evidence is a deterministic recovery path.
- ADS semantic evidence remains authoritative and blocks normal Receive completion.
- Any transition that resolves to normal Receive synchronously commits:
    resultReceiveLatched=true
    resultAction=RECEIVE_TRANSITION_CONFIRMED
    completionStatus=RECEIVE_LATCHED
  BEFORE confirmNormalResultAutomatically() and BEFORE automatic sync enqueue.
- confirmNormalResultAutomatically() now refuses to complete/sync unless the durable Receive latch exists.
- Network/backend failure after completion does not delete the trip; the pre-existing durable sync queue remains
  authoritative and retries later.

no post-result visual gate usage at all, etc.). They were updated only to preserve their original safety invariant:

FINAL PHYSICAL ACCEPTANCE SCENARIO
1. Start Observe and complete a normal trip.
2. Wait for NVU to recognize Concluído / result amount.
3. Tap Receber once, including a fast tap.
4. Result modal disappears permanently.
5. NVU must immediately recognize post-result gameplay with whole-display evidence.
6. Receive latch must be durable before any completion/sync.
7. Trip must enter automatic send; if backend/network is unavailable, it must remain durably queued for retry.
8. Repeat at least five times, including during a capture-surface recovery window.
9. Verify ADS path remains blocked from normal Receive completion.

regression fixtures. Final OEM/device approval still requires running the signed 1.0.93/93 APK on the affected device.
