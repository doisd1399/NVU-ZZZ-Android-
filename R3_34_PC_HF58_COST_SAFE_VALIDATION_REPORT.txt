Android 1.0.110 / versionCode 110
Data da revisão: 18/08/2026
Base: R3.34-PC-HF57 / Android 1.0.109

OBJETIVO
Reduzir custos desnecessários de Google/Firebase/IA sem alterar o comportamento funcional aprovado da HF57 no Observador GTO.

ALTERAÇÕES APLICADAS
1. IA / GEMINI
- Removido @google/genai de package.json e package-lock.json porque estava instalado sem qualquer uso executável.
- Removida a declaração SERVER_SIDE_GEMINI_API de metadata.json.
- Removido vestígio GEMINI_API_KEY do .env.example.
- Auditoria confirma ausência de referências runtime a Gemini/GenAI, Generative Language, Cloud Vision, Maps/Places/Routes, Speech, Translate e Vertex AI nas áreas executáveis verificadas.

2. FIREBASE FUNCTIONS — SINCRONIZAÇÃO DE ESTADO GTO
- Antes de syncGtoTripState, o Android exige FirebaseAuth nativo válido e UID igual ao driverId; sem autenticação válida não é feita chamada Google.
- Retry canônico agressivo foi substituído por backoff: 15s, 30s, 60s, 120s, 240s e teto de 5 min para falhas transitórias.
- Falhas permanentes de contrato/permissão não entram em tempestade de retry.
- Espera local de autenticação não consome callable.
- Callbacks atrasados são isolados por geração e não podem reativar retry de estado antigo.
- syncGtoTripState tornou-se idempotente quando o estado-alvo já foi confirmado no servidor, protegendo contra ACK perdido.

3. FIRESTORE — PROGRESSO DO TRABALHO GTO
- Trabalhos antigos fazem uma única reconciliação histórica segura.
- Após a reconciliação, cada nova viagem atualiza progress atomicamente na mesma transação que cria a viagem, sem reler todo historico_viagens do trabalho.
- Retry duplicado usa o progress já consolidado e não executa nova varredura histórica.
- completedRoutes do modo simple continua preservado e atualizado.

4. PROTEÇÕES DE RELEASE
- audit:firebase-costs foi fortalecido para detectar reintrodução de GenAI/Gemini, retry canônico agressivo, ausência do gate de autenticação, perda da idempotência e regressão do fast path de progresso.
- verify:release agora executa audit:firebase-costs obrigatoriamente.
- Criado test:gto-r3.34-hf58-cost-safe.

LIMITAÇÕES DO AMBIENTE DE VALIDAÇÃO
- O ZIP HF57 original não contém node_modules/tesseract.js/dist/worker.min.js. Por isso npm run build local exige npm install, exatamente como informa o próprio prebuild.
- Este ambiente não tinha acesso ao registry npm, então npm ci/npm --prefix functions ci não puderam ser repetidos aqui.
- Não há Android SDK configurado neste ambiente para executar assembleRelease local.
- A auditoria estrutural mantém os mesmos achados preexistentes da HF57: NavigationProgress.tsx, UploadTest.tsx, PerformanceContext.tsx, Operations.tsx e nvuNewsBackfillService.ts sem caminho de execução; dotenv e react-medium-image-zoom como dependências diretas sem uso. Nenhum desses achados foi introduzido pela HF58.

BARREIRA DE SEGURANÇA DO APK
O workflow HF58 do GitHub foi mantido fail-closed: antes de entregar o APK ele executa npm ci, instala/builda Functions, verify:release (agora incluindo auditoria de custos), build Web, sincronização Capacitor, Gradle assembleRelease, verificação das vozes, assinatura, badging applicationId/version e SHA-256. Se qualquer etapa falhar, o APK de release não é produzido.

DEPLOYMENT
- Para obter as economias Android de retry, gerar/instalar o APK HF58 1.0.110.
- Para ativar idempotência server-side e progresso O(1), publicar também as Firebase Functions HF58 (syncGtoTripState e registerGtoTrip/export correspondente). O workflow de build do APK compila Functions para validação, mas não faz deploy delas automaticamente.

CONCLUSÃO
As alterações HF58 foram deliberadamente limitadas a custo/robustez remota. Os componentes sensíveis do Observador e o comportamento aprovado da HF57 não foram refatorados. Não existe garantia absoluta sem o build e teste físico final do APK no dispositivo, mas não foi detectada regressão funcional nos gates disponíveis; o CI foi configurado para rejeitar o release se a compilação real ou qualquer validação obrigatória falhar.
